# Урок 3. Применяем согласованное предложение

[Открыть исходники этого урока](../../exercises/lesson-05-03-apply/README.md) / [Подсказки рядом с кодом](../../exercises/lesson-05-03-apply/TASK.md)

Мы показали человеку предлагаемую правку, но показ ещё не означает разрешение её записать. Кроме того, между просмотром и согласием файл может измениться: например, его успели исправить вручную. Тогда прежнее предложение относится уже к другой версии исходника.

В `apply_change` свяжем запись с двумя условиями: человек согласился и файл всё ещё совпадает с той версией, для которой подготовили предложение. При отказе файл останется прежним, а при несовпадении контрольной строки программа остановит применение правки.

На этой практике увидим, как согласование становится частью выполнения, а не только фразой в диалоге с моделью. Программа проверяет разрешение непосредственно перед записью и сообщает, была ли она выполнена. Правильность записанного кода проверим следующим шагом.

## Посмотрим на данные

В основном `demo.py` программа покажет diff и спросит согласие в окне Run. Ответ пользователя будет преобразован в `approved`: значение `True` разрешает запись, `False` означает отказ. Для разбора начнём с отказа:

```python
approved = False
# В demo.py согласие задаётся ответом в Run: "да" означает True.
```

При `approved=False` функция должна вернуть `False` без записи. Если согласие получено, сравним текущий хеш файла со значением `before_hash` из словаря `proposal` и только после совпадения запишем `new_text`. ## Соберём функцию с подсказками

У программы есть предложение, но пока нет разрешения его применять. Начнём с отказа: если `approved` равно `False`, сразу вернём `False` и не будем писать файл. Для разрешённого изменения сначала убедимся, что исходный файл всё ещё совпадает с тем, для которого показывали diff.

Допишите уже начатую функцию по заготовке ниже, заполняя каждый `...` по подсказкам. Когда закончите, удалите строку `raise NotImplementedError(...)`; повторно добавлять заголовок `def` не нужно.

```python
def apply_change(root: Path, proposal: dict, approved: bool) -> bool:
    if not approved:
        return False
    path = workspace_path(root, proposal['path'])
    current_hash = hashlib.sha256(path.read_bytes()).hexdigest()
    if current_hash != proposal['before_hash']:
        raise ValueError('Файл изменился после подготовки предложения')
    path.write_text(..., encoding='utf-8')
    return True
```

В `write_text` передайте `proposal["new_text"]` - уже показанный новый текст. Не используйте вместо него `diff`: в diff есть служебные строки, а Python-файлу нужен обычный исходный код. `write_text` заменяет всё содержимое выбранного файла, поэтому согласие и проверка хеша идут раньше.

В каркасе уже найден путь к файлу. Перед этой строкой добавьте ранний выход для отказа, как показано в заготовке, а после неё - проверку хеша и запись нового текста. При первом запуске `demo.py` можно просто нажать Enter в ответ на вопрос: программа должна отклонить запись. Чтобы применить показанную правку, введите `да`. В обоих случаях работаем только с учебным `workspace/prices.py`.

В `demo.py` результат сохраняется строкой `applied = apply_change(ROOT / 'workspace', proposal, approved)`. Если человек отказал, `applied` будет `False`, а файл останется прежним. Если согласие получено, хеш совпал и запись завершилась, функция вернёт `True`; демонстрация напечатает `Изменение применено: True`. Здесь два разных результата работы: запись меняет файл на диске, а возвращаемое логическое значение сообщает вызывающему коду, была ли правка применена. Оно ещё не подтверждает правильность нового кода - это проверим тестами в следующем уроке.

Участие человека в таком решении называют **human-in-the-loop (HITL)**. В нашем примере программа ждёт согласия перед записью, а отказ действительно прекращает применение. Человек включён в выполнение в конкретной точке, а не просто смотрит результат после завершения. Это позволяет задать, какие действия помощник делает сам, а какие требуют решения пользователя. См. [HITL на примере согласования правки](../terms.md#%D1%83%D1%87%D0%B0%D1%81%D1%82%D0%B8%D0%B5-%D1%87%D0%B5%D0%BB%D0%BE%D0%B2%D0%B5%D0%BA%D0%B0).

## Запустим с нашей моделью

После реализации откройте **Project -> lesson-05-03-apply -> demo.py**, щёлкните правой кнопкой внутри редактора и выберите **Run 'demo'**. Результат появится в панели **Run**; её можно открыть через **View -> Tool Windows -> Run**.

Программа получит предложение модели и покажет diff. Затем внизу, в **Run**, появится вопрос о применении. Щёлкните после вопроса, введите `да` и нажмите Enter, только если согласны с показанной правкой. Любой другой ответ означает отказ. Ваша функция `apply_change` должна учесть этот выбор и проверить, что исходный файл не менялся после подготовки предложения. Для первого запуска можно просто нажать Enter и убедиться, что запись отклонена.

Если настройки ещё не сохранены или перестали работать, вернитесь к [уроку подключения модели](../02-note-assistant/04-connect.md). В этом запуске модель не подменяется ответом из файла. Маленькая локальная модель может плохо соблюдать формат JSON; сначала отличите ошибку разбора её ответа от ошибки вашей функции. Если подключение работает, но возможностей модели не хватает, смените модель через `configure_model.py`, сохранив реализацию задания.
