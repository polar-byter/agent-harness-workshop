# Урок 2. Выбираем историю для следующего шага

[Открыть исходники этого урока](../../exercises/lesson-04-02-context/README.md) / [Подсказки рядом с кодом](../../exercises/lesson-04-02-context/TASK.md)

После нескольких действий помощник накопил историю: запросы инструментов и полученные результаты. Перед следующим обращением программа решает, какую часть этой истории снова показать модели. Если убрать нужный результат, модель потеряет сведения, на которые могла опереться; если без отбора передавать всё, объём сообщений будет расти с каждым шагом.

Попробуем простое правило: сохранять исходную задачу и передавать только последние события. Функция `select_context` подготовит такой набор данных, не меняя полную историю запуска. Мы сможем сравнить полную записанную историю с теми событиями, которые программа передаст модели в следующем запросе.

Это упражнение помогает разбирать повторяющиеся или потерявшие цель действия агента: иногда причина находится в составе переданных сообщений. Правило последних событий удобно для первого опыта, но оно не определяет, какие сведения важнее по смыслу. Сейчас изучим само управление доступной информацией; считать токены в этом упражнении не будем.

## Посмотрим на данные

Представим историю из трёх событий и оставим для следующего шага два последних. Для начала обозначим их только номерами, чтобы увидеть работу среза списка:

```python
events = [{'step': 1}, {'step': 2}, {'step': 3}]
events[-2:]  # [{'step': 2}, {'step': 3}]
# Это сокращённые подписи событий только для разбора среза.
```

В настоящей истории на месте каждого такого элемента находится словарь с командой и результатом; функция должна сохранить или исключить его целиком. Число оставляемых событий задаёт `max_events`, а исходную просьбу `task` передаём независимо от этого выбора. При `max_events=0` передаваемая история будет пустой. Этот отбор не пересказывает старые сведения: всё, что исключили из запроса, модель в этом обращении не увидит.

## Соберём функцию с подсказками

Сейчас в истории три события, а следующему шагу хотим передать только два последних. При этом исходную просьбу пользователя терять нельзя. Поэтому создадим новый словарь: задача останется прежней, а список событий выберем заново.

Допишите уже начатую функцию по заготовке ниже, заполняя каждый `...` по подсказкам. Когда закончите, удалите строку `raise NotImplementedError(...)`; повторно добавлять заголовок `def` не нужно.

```python
def select_context(task: str, events: list[dict], max_events: int) -> dict:
    if type(max_events) is not int or max_events < 0:
        raise ValueError('Нужен неотрицательный целый max_events')
    context = {'task': task, 'events': []}
    if max_events > 0:
        context['events'] = ...
    return context
```

В пропуске используйте `events[-max_events:]`. При `max_events=2` получатся события с номерами 2 и 3 из нашего примера. Двоеточие в квадратных скобках обозначает срез - новый список из выбранной части. Сам `events` от этого не меняется.

Нулевой случай уже обеспечен заготовкой: `context["events"]` останется `[]`. Это важно, потому что `events[-0:]` равнозначно `events[0:]` и вернуло бы всю историю. Для нашего упражнения событие содержит команду вместе с результатом; внутри отдельного события ничего не обрезаем.

Вызов из `demo_check.py` вернёт словарь `{'task': 'Найди Python', 'events': [{'step': 2}, {'step': 3}]}`. В нём исходная задача сохранена, а для следующего обращения выбраны два последних события. `return context` передаёт этот новый словарь управляющему коду; сама функция ещё не отправляет сообщения модели. Подготовленный запуск использует выбранную задачу и историю при обращении за следующим решением.

Здесь мы затронули **управление контекстом (context engineering)**: приложение выбирает, какие сведения будут доступны модели при обращении. Это шире формулировки одной просьбы - значение имеют также правила, исходные данные и история. Наш отбор последних событий показывает только одну часть этой работы. Он не определяет важность сведений по смыслу, но позволяет увидеть сам момент выбора данных. См. [контекст на примере нашего помощника](../terms.md#%D1%83%D0%BF%D1%80%D0%B0%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5-%D0%BA%D0%BE%D0%BD%D1%82%D0%B5%D0%BA%D1%81%D1%82%D0%BE%D0%BC).

## Запустим с нашей моделью

После реализации откройте **Project -> lesson-04-02-context -> demo.py**, щёлкните правой кнопкой внутри редактора и выберите **Run 'demo'**. Результат появится в панели **Run**; её можно открыть через **View -> Tool Windows -> Run**.

Перед очередным обращением к модели программа вызывает вашу функцию `select_context`. В Run появятся статус, ответ и история. Посмотрите, какие события оставляет выбранный `max_events`: исключённые из текущего запроса события модель в нём не видит. Формулировка ответа может измениться; сравнивать нужно переданные данные и поведение.

Если настройки ещё не сохранены или перестали работать, вернитесь к [уроку подключения модели](../02-note-assistant/04-connect.md). В этом запуске модель не подменяется ответом из файла. Маленькая локальная модель может плохо соблюдать формат JSON; сначала отличите ошибку разбора её ответа от ошибки вашей функции. Если подключение работает, но возможностей модели не хватает, смените модель через `configure_model.py`, сохранив реализацию задания.

## Проверим функцию отдельно

Для воспроизводимого примера откройте **Project -> lesson-04-02-context -> demo_check.py** и выберите **Run 'demo_check'**. Этот файл обращается к подготовленным данным без модели. До завершения текущей функции он показывает "Допишите ...", после реализации ожидаем:

```text
{'task': 'Найди Python', 'events': [{'step': 2}, {'step': 3}]}
```

Дополнительно можно запустить `tests/test_lesson.py` через Run по классу `LessonTests`. Эти проверки помогают обнаружить ошибку функции независимо от поведения модели.
