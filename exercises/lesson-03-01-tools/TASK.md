# Подсказки к текущему заданию

Пользователь просит: "Найди заметки о Python". Модель предлагает вызвать `find_notes` с запросом `python` - подходящее действие для нашей программы. Но она может написать и другое название, например `search_notes`, хотя такой функции у нас нет. Даже правильно записанный JSON не делает предложение модели допустимой командой.

Между ответом модели и выполнением действия поставим свою проверку. Функция `dispatch_tool` будет знать только два разрешённых инструмента: чтение заметок и поиск. Неизвестное название она отклонит, для поиска потребует текстовый запрос, а путь к файлу возьмёт у программы. Модель сможет предложить действие, но не сможет одной строкой добавить программе новую возможность.

В этом и состоит смысл упражнения: отделить выбор модели от правил выполнения, которые задаём мы. Напишем такой механизм на двух знакомых функциях и проверим его как на правильной команде, так и на выдуманном названии. Это поможет понимать, где приложение действительно ограничивает действия агента, а где лишь просит модель соблюдать инструкцию.

Откройте `agent.py` -> функция `dispatch_tool`.

Теперь выразим правило допуска в коде. Если модель написала `read_notes`, программа вызовет подготовленное чтение заметок; если `find_notes` - проверит поисковый запрос и выполнит поиск. Ни одно другое название не должно приводить к действию. Поэтому в конце функции будет ошибка для неизвестного инструмента, а не попытка угадать, что имела в виду модель.

Такой выбор разрешённой функции по имени называют диспетчеризацией. В нашем помощнике он одновременно задаёт границу доступных действий: инструкция объясняет модели, что можно запросить, а `dispatch_tool` проверяет, что именно она запросила. Здесь правила приложения начинают действовать независимо от того, насколько точно модель выполнила промпт.

Допишите уже начатую функцию по заготовке ниже, заполняя каждый `...` по подсказкам. Когда закончите, удалите строку `raise NotImplementedError(...)`; повторно добавлять заголовок `def` не нужно.

```python
def dispatch_tool(command: dict, notes_path: Path) -> dict:
    name = command.get('tool')
    if name == 'read_notes':
        return {'notes': ...}
    if name == 'find_notes':
        query = command.get('query')
        if not isinstance(query, str):
            raise ValueError('Для поиска нужна строка query')
        notes = read_notes(notes_path)
        return {'matches': ...}
    raise ValueError('Неизвестный инструмент: ' + str(name))
```

В ветке `read_notes` подставьте вызов `read_notes(notes_path)`. В ветке поиска заметки уже прочитаны в `notes`; передайте их вместе с `query` в `find_notes`. Мы используем существующие функции, а не дублируем их код.

Если поля `tool` нет, вызов `command.get("tool")` вернёт `None`, и выполнение дойдёт до ошибки неизвестного инструмента. Для поиска дополнительно проверяем `isinstance(query, str)`, чтобы не передать число или список вместо текста. Путь при этом всегда берём из параметра `notes_path`, который задаёт программа.

На нашей команде с запросом `python` функция сначала прочитает заметки, а затем получит от поиска список `['Python functions return values.', 'Python lists keep item order.']`. Этот список она поместит в словарь под ключом `matches`. Поэтому результатом вызова `result = dispatch_tool(command, notes_path)` станет `{'matches': ['Python functions return values.', 'Python lists keep item order.']}`. В `result['matches']` вызывающий код найдёт строки для передачи модели. Здесь ваша функция уже выполнила поиск; `return` только передаёт найденные данные дальше и сам не отправляет их модели.

Такие ограничения часто называют **гардрейлами (guardrails)**. В нашем случае это конкретные проверки перед действием: разрешённое название инструмента и строковый запрос. Они выполняются кодом, поэтому выдуманное название будет отклонено независимо от того, как уверенно модель его предложила. Гардрейлы бывают разными; наши проверки не подтверждают правильность ответа по смыслу. Другие примеры из курса собраны в памятке о гардрейлах.

## Проверим выдуманное название

После успешного контрольного запуска откройте `demo_check.py`. Внутри `main` найдите словарь, который передаётся в `dispatch_tool`, и замените только значение поля `tool`: вместо `'find_notes'` напишите `'search_notes'`. Функцию `dispatch_tool` и её ветки оставьте прежними. Мы намеренно подставляем команду, похожую на поиск, но не предусмотренную приложением.

Запустите этот же файл через Run. Ожидаем `ValueError: Неизвестный инструмент: search_notes`. До вызова чтения или поиска программа не дойдёт: для этого названия нет разрешённой ветки. Так проверяется ограничение в коде, даже если модель уверенно предложила бы такое действие. После опыта верните `'find_notes'` в демонстрационную команду.

Это ограничение проверяет допустимость действия и тип запроса, но не выбирает правильный запрос за модель. Если она попросит разрешённый поиск по другому слову, функция выполнит его. Сопоставление команды с задачей пользователя остаётся отдельной проверкой поведения помощника. Теперь у нас есть способ различить эти случаи: программа отклонила недопустимое действие или выполнила разрешённое, которое модель выбрала неудачно.
