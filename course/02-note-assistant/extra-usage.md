# Посмотрим статистику настоящего запроса

[Открыть исходники этого урока](../../exercises/lesson-02-extra-usage/README.md) / [Подсказки рядом с кодом](../../exercises/lesson-02-extra-usage/TASK.md)

Модель уже ответила на нашу заметку. А сколько текста она получила? Что заняло время: загрузка модели, чтение запроса или создание ответа? И почему длинная переписка требует всё больше ресурсов, хотя последний вопрос занимает одну строку?

Добавим к ответу доступные показатели сервиса и проведём опыты на знакомом вопросе о Python. Это позволит обсуждать медленный запуск или растущий запрос по наблюдаемым данным: сколько токенов было передано, сколько сгенерировано и какие сведения о времени сообщил сервис. Отсутствующий показатель научимся отличать от измеренного нуля.

Для такой проверки напишем небольшую функцию оформления статистики. Заодно разберём, чем контекстное окно отличается от фактически переданного текста и какие сведения можно получить о кеше. По основному маршруту уже можно идти дальше; этот необязательный урок помогает понять расход ресурсов и читать результаты запусков без догадок по одной скорости появления ответа.

## Откроем отдельную папку

Откройте [архив практикума](../../downloads/lesson-02-extra-usage.zip?raw=true), выберите в Проводнике **Извлечь всё**. Внутри находится папка `lesson-02-extra-usage`. Откройте её в PyCharm через **File -> Open**. Прошлый проект и ваши решения останутся в своей папке.

В панели **Project -> lesson-02-extra-usage** найдите три файла:

| Файл | Что с ним делаем |
|---|---|
| `model_stats.py` | Дописываем небольшую функцию оформления показателей |
| `demo_usage.py` | Запускаем настоящий запрос и смотрим результат в Run |
| `usage_client.py` | Читаем готовое получение ответа и его статистики |

Каркас прочитает подключение, сохранённое в основном уроке, поэтому повторно вводить ключ или скачивать модель не потребуется. Готовый `transport.py` остался прежним; его путь от сообщений до ответа разобран в [отдельной статье](extra-send-live.md).

Перед упражнением договоримся о названиях показателей. Модель обрабатывает текст небольшими фрагментами, токенами: по входному счётчику увидим объём инструкции, вопроса и заметки, по выходному - объём созданного продолжения. Если сервис сообщает о повторном использовании прежних вычислений для части входа, он может отдельно указать токены из кеша. Это не число ответов, которые модель просто запомнила; подробнее разберём его после первого вывода статистики.

## Почему статистику нужно взять раньше

В основном `send_live` ответ сервиса превращается в знакомый словарь `status` и `output`. Для ответа по заметкам этого хватает, но дополнительные поля сервиса в него не переносятся. `answer_question` возвращает текст ответа без показателей расхода. По этому тексту нельзя определить, сколько входных токенов обработал сервис, поэтому показатели нужно прочитать из его исходного ответа.

Поэтому в `usage_client.py` подготовлена функция `request_sample`: она получает исходный ответ сервиса и передаёт его в `collect_usage`, чтобы прочитать показатели до преобразования ответа в текст для пользователя. Вопрос, заметка и параметры те же, что в основном опыте, но у диагностики свой запуск; менять `send_live` в остальных уроках не нужно.

## Соберём вывод с подсказками

Мы уже получаем статистику готовым кодом, а в функции `format_usage` оформим её для вывода. Функция примет словарь показателей и вернёт три строки; сам запрос и печать останутся в `demo_usage.py`. Такое разделение позволит проверить оформление на известных числах ещё до обращения к модели.

Перед настоящим обращением `demo_usage.py` передаст ей маленький контрольный пример:

```python
{'input_tokens': 10, 'output_tokens': 0, 'cached_tokens': None}
```

Это специально подобранные входные данные для проверки функции, не измерения модели. Десять нужно показать как число, ноль сохранить нулём, а отсутствие значения `None` объяснить словами.

В консоли хотим увидеть `Токены запроса: 10`. В словаре число `10` хранится под ключом `'input_tokens'`, поэтому в коде свяжем название для вывода с этим ключом: `('Токены запроса', 'input_tokens')`. Аналогично подготовим ещё две пары для токенов ответа и кеша. Так одна и та же последовательность действий сможет оформить все три показателя.

Откройте **Project -> lesson-02-extra-usage -> model_stats.py**. Эти пары и начало функции уже записаны в каркасе. Внутри цикла замените `NotImplementedError` по такой заготовке:

```python
def format_usage(stats: dict) -> list[str]:
    lines = []
    for label, key in (
        ('Токены запроса', 'input_tokens'),
        ('Токены ответа', 'output_tokens'),
        ('Токены из кеша', 'cached_tokens'),
    ):
        value = stats.get(key)
        if ___:
            value = ___
        lines.append(___)
    return lines
```

В первый пропуск поставьте проверку `value is None`. Во второй - строку `'сервис не сообщил'`. В третий - строку с названием и значением: `f'{label}: {value}'`. Префикс `f` позволяет подставить значения из фигурных скобок; `lines.append(...)` добавит собранную строку в список.

Проследим первый проход цикла на нашем контрольном словаре. Запись `for label, key in ...` берёт первую пару: её значение `'Токены запроса'` попадает в переменную `label`, а `'input_tokens'` - в `key`. Затем `stats.get(key)` находит число `10`. Из названия и числа выражение `f'{label}: {value}'` собирает строку `Токены запроса: 10`, которую добавляем в `lines`. На следующих проходах так же оформляются показатели ответа и кеша.

В нашем примере для кеша записано `None`; тот же результат вернёт `stats.get(key)`, если ключа вообще нет в словаре. В обоих случаях выводим "сервис не сообщил". Здесь нельзя заменить условие на `if not value`: ноль тоже считается ложным, хотя для счётчика он является полноценным результатом. `return lines` оставляем после цикла, чтобы получить все три строки.

Сохраните файл. Откройте `demo_usage.py`, нажмите правой кнопкой **в редакторе -> Run 'demo_usage'**. Вывод появится в панели **Run** снизу; если она скрыта, откройте **View -> Tool Windows -> Run**. Пока заглушка не удалена, программа покажет просьбу закончить функцию и не обратится к модели.

Когда функция готова, запуск сделает одно настоящее обращение. Сначала появится ответ, затем три строки токенов и время. Для Ollama дополнительно выводятся запрошенный `num_ctx` и скорость генерации, если ответ содержит нужную длительность. Повторный Run делает новый запрос; у облачного сервиса он расходует доступную квоту или баланс.

На контрольных данных результатом функции будет список `['Токены запроса: 10', 'Токены ответа: 0', 'Токены из кеша: сервис не сообщил']`. После `return lines` этот список получит `demo_usage.py` и напечатает его строки по очереди. Наша функция только превращает уже полученные показатели в понятный текст: она не считает токены сама и не меняет ответ сервиса.

## Что именно считают токены

Когда мы передаём фразу о Python, токенизатор модели разбивает её на небольшие фрагменты: слова, части слов или знаки. Эти фрагменты и называются токенами. Разбиение зависит от токенизатора, поэтому длина строки `len(question)` в символах не покажет число обработанных токенов.

Вход нашего обращения состоит из инструкции, вопроса и заметки. При подготовке сообщения к нему также применяется служебное оформление модели. Поэтому число входных токенов не обязано совпасть с длиной одного видимого вопроса. Выходные токены относятся к сгенерированному продолжению; у некоторых моделей в учёт входят также внутренние рассуждения. Не приравнивайте этот счётчик к количеству напечатанных слов.

Для Ollama мы читаем `prompt_eval_count` и `eval_count`. Для облачных подключений пробуем поля `usage.prompt_tokens` и `usage.completion_tokens`. Мы переименовали их в общие `input_tokens` и `output_tokens` только внутри учебного клиента. Отсутствующее поле остаётся `None`. Форматы описаны в [API Ollama](https://docs.ollama.com/api/chat) и [учёте OpenRouter](https://openrouter.ai/docs/cookbook/administration/usage-accounting).

## Контекстное окно: что помещается в одно обращение

Сейчас в `notes` одна строка. Представим, что вместо неё отправили регламент на сотню страниц, историю переписки и результаты инструментов. Всё это заняло бы место во входе, а для продолжения ответа тоже потребовались бы токены. Размер контекстного окна ограничивает объём, с которым модель может работать в таком обращении; конкретное распределение лимитов зависит от модели и API.

В локальном запросе мы задаём `num_ctx=4096`. Поэтому в Run написано именно **Запрошенный num_ctx**, а не "модель запомнила 4096 токенов". Это настройка, не измерение заполненности окна и не доказательство фактически выделенного объёма. `num_predict=1200` задаёт верхнюю границу генерации, а не уже потраченные токены. Для облачного подключения размер окна наш ответ не сообщает, и клиент не выдумывает его по лимиту ответа.

Контекст не равен обученным знаниям и не пополняется просто оттого, что на диске лежит ещё один файл. В запрос попадает только то, что передала программа. Длинная история чата становится частью нового входа, когда приложение снова отправляет её модели. В нашем опыте `demo_usage.py` каждый раз собирает новый запрос с одной заметкой; предыдущий Run туда автоматически не добавляется.

## Внимание: как связываются части контекста

Вернёмся к нашему примеру. Вопрос спрашивает о Python, а заметка сообщает, что списки сохраняют порядок. Чтобы продолжить текст подходящим ответом, модели нужно учитывать связи между этими частями, а не только последнее слово вопроса.

Связи между частями текста учитывает механизм внимания, attention. Во время вычислений он позволяет использовать представления других токенов при обработке текущего; вклад этих представлений зависит от вычисленных весов. Этот механизм уже находится внутри модели, и наш клиент его не реализует. Название описывает математическую операцию, поэтому само по себе не обещает, что модель правильно применит нужный пункт регламента. Исходная работа - [Attention Is All You Need](https://arxiv.org/abs/1706.03762).

Наши счётчики показывают объём обработанного текста, но по ним нельзя узнать, какие сведения модель использовала для ответа. Например, регламент может целиком поместиться в запрос, а модель всё равно пропустит нужное исключение и ответит по общему правилу. Поэтому после запуска сверяем ответ с соответствующим пунктом регламента: одного факта, что документ поместился, для проверки недостаточно.

## Кеш: какую работу можно не повторять

Пока модель создаёт ответ токен за токеном, уже обработанные части запроса остаются прежними. KV-кеш хранит часть промежуточных результатов внимания, чтобы не вычислять их заново на каждом шаге. Это рабочие данные запуска, не изменение обученных параметров. [Разбор KV-кеша в Transformers](https://huggingface.co/docs/transformers/cache_explanation).

Есть и другая практическая ситуация: несколько обращений начинаются одинаковой длинной инструкцией и документом. При поддержке prompt caching сервис может повторно использовать вычисления для совпадающего начала. Условия, минимальная длина и срок хранения зависят от провайдера. Это не обязательно кеш уже готового ответа. [Кеширование запросов в OpenRouter](https://openrouter.ai/docs/guides/best-practices/prompt-caching).

В нашем выводе строка о кеше отражает только сообщённый счётчик: `prompt_eval_cached_count` у поддерживающей его версии Ollama либо `usage.prompt_tokens_details.cached_tokens` у облачного сервиса. Значение `0` означает сообщённый ноль. "Сервис не сообщил" означает отсутствие этого поля, а не доказанное отсутствие всех видов кеширования.

Кешированные входные токены не нужно прибавлять ещё раз к общему входу. И один более быстрый повтор не доказывает попадание в кеш: модель могла уже загрузиться в память, поменялась нагрузка или длина ответа. Обсуждать экономию денег тоже можно только по правилам и фактическим начислениям выбранного сервиса.

## Три небольших опыта

Сначала запустите `demo_usage.py` без изменения вопроса и заметки. Сохраните из Run ответ, счётчики и время. Для повторения используйте ту же модель и настройки. Если показатель отсутствует, так и запишите: его нельзя заменить удобным предполагаемым числом.

Затем в `main` файла `demo_usage.py` измените только `notes`. Первую строку оставьте прежней, рядом добавьте другую:

```python
notes = [
    'Python lists keep item order.',
    'Словари Python хранят пары ключ-значение.',
]
```

Теперь в запросе больше исходных данных. Посмотрите, изменилось ли число входных токенов. Если оно не выросло, сначала проверьте сохранённый файл, запускаемую папку и наличие показателя, а не делайте вывод о чудесном сжатии. Заметку добавляем именно здесь; другие файлы менять не требуется.

Наконец верните исходный список из одной заметки и дважды повторите запрос. Сопоставьте доступный счётчик кеша, время и длину ответа. Это знакомство с наблюдением, не строгий замер производительности. Даже без видимого кеша мы уже научились отличать измерение от предположения.

Время обращения измеряет готовый клиент через `perf_counter`: от начала вызова `request_json` до возвращения данных. В него входят ожидание сервиса, возможная загрузка модели, вычисления и передача ответа. Скорость Ollama считается отдельно по `eval_count / (eval_duration / 1_000_000_000)`: длительность приходит в наносекундах. Делить токены ответа на всё время и называть результат чистой скоростью модели было бы неточно.
