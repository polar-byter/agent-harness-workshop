# Урок 1. Выполняем команду поиска

[Открыть исходники этого урока](../../exercises/lesson-03-01-tools/README.md) / [Подсказки рядом с кодом](../../exercises/lesson-03-01-tools/TASK.md)

> **Где мы.** До сих пор пункт регламента для модели выбирали мы сами. Теперь модель сможет попросить программу найти нужные пункты. Сегодня - первая половина: программа принимает просьбу модели и решает, выполнять ли её.
> `задача -> модель -> [команда -> проверка -> поиск] -> результат`

Клиент спрашивает о возврате. Модель отвечает не текстом, а просьбой: выполни `find_notes` с запросом "возврат". Но она может написать и `search_notes`, хотя такой функции у нас нет, или попросить `delete_file`. Правильно оформленный JSON ещё не делает просьбу допустимой.

Поэтому между ответом модели и действием поставим проверку. Функция `dispatch_tool` будет знать ровно два разрешённых действия: прочитать регламент и найти в нём пункты. Любое другое название она отклонит, для поиска потребует текстовый запрос, а путь к файлу возьмёт у программы. Модель сможет попросить, но не сможет одной строкой добавить программе новую возможность. Именно здесь проходит граница, которую во введении мы обещали администратору: права агента задаются в коде, а не в промпте.

## Посмотрим на данные

На задачу "найди в регламенте пункты о возврате" модель возвращает текст, который `decide_live` превращает в словарь:

```python
command = {'type': 'tool', 'tool': 'find_notes', 'query': 'возврат'}
command.get('tool')   # 'find_notes'
```

Поле `type` со значением `tool` означает, что модель просит выполнить действие. В `tool` - название действия, в `query` - текст для поиска. Наша функция получит этот словарь, выберет по названию нужную функцию и вернёт результат.

Путь к регламенту передаётся отдельным параметром `notes_path`, и задаёт его программа. Поэтому модель может попросить прочитать или обыскать регламент, но не может выбрать другой файл на компьютере.

Такой формат просьбы - учебный протокол курса. Крупные API предлагают для этого встроенный механизм function calling, но принцип тот же: модель описывает желаемое действие, а выполняет его программа.

## Напишите сами

Замените в `dispatch_tool` строку `raise NotImplementedError(...)` кодом ниже и заполните пропуски:

```python
    if name == 'read_notes':
        return {'notes': ...}
    if name == 'find_notes':
        query = command.get('query')
        if not isinstance(query, str):
            raise ValueError('Для поиска нужна строка query')
        notes = read_notes(notes_path)
        return {'matches': ...}
    raise ValueError('Неизвестный инструмент: ' + str(name))
```

1. В ветке `read_notes` вызовите `read_notes(notes_path)`.
2. В ветке поиска пункты уже прочитаны в `notes`; передайте их вместе с `query` в `find_notes`.

Мы используем функции из первого раздела, а не пишем поиск заново. Последняя строка срабатывает для любого названия, кроме двух разрешённых: программа не пытается угадать, что имела в виду модель. Если поля `tool` в словаре нет вовсе, `command.get('tool')` вернёт `None`, и выполнение тоже дойдёт до этой ошибки. Проверка `isinstance(query, str)` не даст передать в поиск число или список вместо текста.

Выбор функции по имени программисты называют диспетчеризацией. В нашем помощнике она заодно задаёт границу возможностей агента.

## Запустим с моделью

Откройте `demo.py` и выберите **Run 'demo'**. Модель получит просьбу найти пункты о возврате, вернёт команду, `demo.py` покажет её в Run и передаст в вашу функцию. Ожидаем команду `find_notes` с запросом про возврат и словарь с найденными пунктами.

Если модель ответила сразу текстом или выбрала другой инструмент, сравните её команду с задачей: программа не подменяет решение модели готовым ответом. Маленькие локальные модели иногда нарушают формат JSON, тогда `decide_live` сообщит об этом. Если такое повторяется, смените модель через `configure_model.py`; ваша функция при этом не меняется.

## Проверим функцию отдельно

Откройте `demo_check.py` и выберите **Run 'demo_check'**. Здесь команда задана заранее, без модели, поэтому результат всегда одинаковый:

## Попробуйте сломать

В `demo_check.py` найдите словарь, который передаётся в `dispatch_tool`, и замените значение `'find_notes'` на `'search_notes'`. Запустите снова. Ожидаем `ValueError: Неизвестный инструмент: search_notes`: до чтения файла и поиска дело не дойдёт. Так проверяется граница в коде, как бы уверенно модель ни предложила выдуманное действие. Верните `'find_notes'`.

Учтите, что проверка отсекает недопустимые действия, но не выбирает правильный запрос за модель. Если модель попросит разрешённый поиск по слову "доставка", функция его выполнит. Подходит ли такой поиск к задаче клиента - отдельный вопрос, и теперь его можно отличить от первого: программа отклонила недопустимое действие или выполнила разрешённое, которое модель выбрала неудачно.

## Что мы получили

Модель может попросить поиск, а программа решает, выполнять ли просьбу. Такие проверки и ограничения в статьях об ИИ называют **гардрейлами**, по-английски guardrails. Наши - простые условия Python: разрешённое название и строковый запрос. Другие примеры гардрейлов в курсе собраны в [памятке терминов](../terms.md#%D0%B3%D0%B0%D1%80%D0%B4%D1%80%D0%B5%D0%B9%D0%BB%D1%8B).

Найденные пункты пока остались у программы: модели их ещё никто не передал. Это следующий шаг: [возвращаем результат модели](02-cycle.md). Вернуться к [оглавлению и архивам](../README.md).
