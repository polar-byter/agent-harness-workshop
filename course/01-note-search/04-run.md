# Урок 4. Соединяем чтение, поиск и журнал в один рабочий инструмент

[Открыть исходники этого урока](../../exercises/lesson-01-04-run/README.md) / [Подсказки рядом с кодом](../../exercises/lesson-01-04-run/TASK.md)

> **Где мы находимся:** Мы создали три самостоятельных кирпичика:
> 1. `notes.py` умеет считывать регламент с диска и очищать строки (`read_notes`).
> 2. `notes.py` умеет искать пункты по ключевому слову (`find_notes`).
> 3. `journal.py` умеет дописывать результат в нестираемый лог JSONL (`write_result`).
> 
> Сейчас мы объединим их в одну главную функцию-дирижёр — `run_search` в файле `app.py`. Это и будет наш первый полноценный инструмент (Tool), готовый для будущего ИИ-агента:
> 
> `[файл регламента -> чтение -> поиск -> запись в журнал] -> готовый структурированный ответ`

Пока что для выполнения поиска нам приходилось в тестовом скрипте вручную вызывать функции одну за другой: сначала прочитай, потом передай результат в поиск, потом собери словарь, потом не забудь вызвать запись в файл.

Когда в третьем разделе курса мы подключим языковую модель, нейросеть не сможет жонглировать десятком мелких функций. Модели нужен один простой и надёжный инструмент:
> *«Сделай поиск по запросу "возврат" и верни мне понятный ответ»*.

А программа вокруг модели (наш **harness**) должна сама под капотом открыть файл, отфильтровать текст, сохранить аудит-лог и вернуть чистый структурированный результат.

Кроме того, результат поиска должен содержать чёткий статус:
* `'found'` — если совпадения найдены.
* `'not_found'` — если в регламенте ничего подходящего не оказалось.

Благодаря статусу вызывающей программе (или нейросети) не придётся проверять длину списков — исход поиска ясен с первого взгляда.

---

## Что поступает на вход и что получается на выходе

Наша главная функция `run_search` принимает три параметра:
1. `notes_path` — где лежит файл регламента (`data/notes.txt`).
2. `query` — поисковая фраза клиента (например, `' возврат '`).
3. `journal_path` — куда сохранять лог (`runs.jsonl`).

А возвращает единый аккуратный словарь:

```python
{
    'query': 'возврат',
    'status': 'found',
    'matches': [
        'Возврат товара возможен в течение 14 дней.',
        'ВОЗВРАТ денег производится на карту покупателя.',
        'Для возврата нужен чек или номер заказа.',
    ]
}
```

### Как вычисляется статус?
В Python есть элегантная форма сокращённой проверки условия (тернарный оператор):

```python
status = 'found' if matches else 'not_found'
```

Она читается буквально как живая речь:
*«Положи в переменную `status` строку `'found'`, если список `matches` не пустой, иначе положи `'not_found'`»*.

> **Попробуйте угадать до запуска:** Сколько пунктов из шести найдёт запрос со словом «возврат» в нашем файле? Два или больше? Внимательно посмотрите на четвёртый пункт правил магазина.

## Напишите код сами

Удалите строчку `raise NotImplementedError(...)` и допишите сценарий, заполнив пропуски `...`:

```python
    status = 'found' if matches else 'not_found'
    result = {
        'query': ...,
        'status': ...,
        'matches': ...,
    }
    write_result(..., ...)
    return result
```

1. В поле `'query'` сохраните очищенный от крайних пробелов запрос: `query.strip()`.
2. В поля `'status'` и `'matches'` подставьте переменные `status` и `matches`.
3. В функцию `write_result` передайте два аргумента по порядку: путь к журналу `journal_path` и созданный словарь `result`.
4. Строка `return result` отдаст готовый отчёт наружу.

### Совпало с вашей догадкой?
Нашлось целых **три** пункта! Почему нашёлся третий пункт: *«Для возврата нужен чек или номер заказа»*?
Потому что наш простой поиск ищет вхождение подстроки. Корень слова *«возврат»* целиком входит в слово *«возврат-а»*. 

Для поиска по регламенту это очень удобно: клиенты часто пишут слова в разных падежах («о возврате», «для возврата»), и простая проверка подстроки часто ловит нужные формы без сложных лингвистических библиотек.

## Под капотом: как устроен проект урока и ключевые модули

Давайте подведём архитектурный итог первого подпроекта и посмотрим, как взаимодействуют все модули.

### Карта файлов и архитектурные роли

```text
lesson-01-04-run/
├── data/
│   └── notes.txt          # Слой данных (хранилище регламента)
├── notes.py               # Доменный слой (чистая логика чтения и фильтрации текста)
├── journal.py             # Инфраструктурный слой (сохранение на диск в формате JSONL)
├── app.py                 # Слой приложения / Координатор (связывает логику и инфраструктуру)
├── demo.py                # Точка входа для демонстрации и ручной проверки
└── runs.jsonl             # Результат работы (журнал аудита)
```

### Паттерн «Координатор» (Orchestrator / Facade)
Обратите внимание на чистоту архитектуры:
* Модуль `notes.py` понятия не имеет о существовании `journal.py`. Он не знает, куда будут записываться результаты и будут ли записываться вообще.
* Модуль `journal.py` понятия не имеет, откуда взялся словарь `result` — из поиска по заметкам, из веб-запроса или из вызова нейросети.
* И только модуль `app.py` импортирует функции из обоих модулей и координирует их совместную работу.

Такое разделение обязанностей называется **Separation of Concerns (разделение ответственности)**. Если завтра мы решим сохранять журнал не в текстовый файл, а в базу данных PostgreSQL или сервис ClickHouse, нам потребуется изменить только `journal.py` — функции поиска и чтения в `notes.py` останутся нетронутыми!

### Почему порядок действий в `run_search` именно такой?

Посмотрим на тело функции `run_search`:
```python
def run_search(notes_path: Path, query: str, journal_path: Path) -> dict:
    notes = read_notes(notes_path)        # 1. Чтение с диска
    matches = find_notes(notes, query)     # 2. Поиск в памяти
    status = 'found' if matches else 'not_found'
    result = {                            # 3. Формирование контракта ответа
        'query': query.strip(),
        'status': status,
        'matches': matches,
    }
    write_result(journal_path, result)    # 4. Запись в аудит-лог
    return result                         # 5. Возврат результата
```

Этот порядок детерминирован и безопасен:
1. Самая рискованная операция (чтение с диска) идёт первой. Если файла нет или нет прав — функция прерывается до того, как потрачены ресурсы.
2. Чистая обработка данных происходит в быстрой оперативной памяти.
3. Логирование происходит строго перед возвратом данных.
