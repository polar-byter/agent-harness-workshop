# Урок 2. Возвращаем результат модели

[Открыть исходники этого урока](../../exercises/lesson-03-02-cycle/README.md) / [Подсказки рядом с кодом](../../exercises/lesson-03-02-cycle/TASK.md)

> **Где мы.** Программа выполняет просьбу модели найти пункты регламента. Но найденное пока остаётся у программы. Сегодня замкнём круг: результат поиска уйдёт модели, и она сможет ответить клиенту.
> `задача -> модель -> поиск -> [результат -> снова модель] -> ответ`

Это ровно то место, где в случае MWS мог потеряться нужный пункт: поиск его нашёл, а до модели он не дошёл. Модель не помнит прошлых обращений. Если в следующий раз снова отправить ей только задачу "найди пункты о возврате", она не узнает, что поиск уже выполнен, и попросит его ещё раз.

Поэтому программа будет вести историю: каждую команду модели вместе с результатом её выполнения. При следующем обращении модель получит исходную задачу и эту историю. Тогда она сможет ответить по найденным пунктам или попросить ещё одно действие. Повторение такого обмена и называют агентным циклом.

## Откроем каркас

Скачайте [архив урока](../../downloads/lesson-03-02-cycle.zip?raw=true), распакуйте и откройте папку `lesson-03-02-cycle` через **File -> Open**. Сегодняшнее задание - функция `run_agent` в файле `agent.py`. `dispatch_tool` из прошлого урока в ней уже готова.

## Как устроен цикл

```text
Задача и история -> решение модели
                       |
             +---------+---------+
             |                   |
       просьба о действии   готовый ответ
             |                   |
       выполнение поиска     завершение
             |
       результат в историю
             |
       новое решение модели
```

Цикл организует функция `run_agent`. На каждом шаге она вызывает `decide`, чтобы узнать решение модели. Если пришёл готовый ответ, работа закончена. Если пришла просьба о действии, `dispatch_tool` выполняет её, а команда и результат добавляются в список `events`. Число шагов ограничено параметром `max_steps`: если модель так и не ответит, программа остановится сама.

## Посмотрим на данные

Функция `decide` получает задачу `task` и историю `events` и возвращает следующую команду или готовый ответ. В `demo.py` эту роль играет `decide_live`, которая обращается к модели, а в `demo_check.py` - `decide_fixture` с заранее известным поведением: на первом шаге она просит поиск, на втором отвечает.

Одно событие в истории выглядит так:

```python
events.append({'command': {'tool': 'find_notes', 'query': 'возврат'},
               'result': {'matches': ['Возврат товара возможен в течение 14 дней.', ...]}})
```

На анимации видно, как после поиска в новый запрос к модели уходят исходная задача, команда и найденные пункты, а счётчик обращений растёт с одного до двух. Настоящая модель может пойти и другим путём, например сначала прочитать весь регламент.

## Напишите сами

В `run_agent` уже есть проверка `max_steps` и пустой список `events`. Замените `raise NotImplementedError(...)` циклом и заполните два пропуска:

```python
    for step in range(max_steps):
        command = decide(task, events)
        if command.get('type') == 'answer':
            text = command.get('text')
            if not isinstance(text, str) or not text.strip():
                raise ValueError('Пустой ответ')
            return {'status': 'completed', 'answer': text, 'events': events}
        if command.get('type') != 'tool':
            raise ValueError('Ожидался ответ или запрос инструмента')
        result = ...
        events.append({'command': ..., 'result': ...})
    return {'status': 'step_limit', 'answer': '', 'events': events}
```

1. В `result` сохраните `dispatch_tool(command, notes_path)`.
2. В событие положите переменные `command` и `result`.

`range(max_steps)` задаёт, сколько раз цикл может обратиться к модели. `return` внутри ветки ответа сразу завершает всю функцию. Последний `return` стоит после цикла и срабатывает, только если шаги кончились, а ответа так и не было: тогда статус `step_limit`.

Проследим контрольный пример. На первом шаге `events` пуст, и `decide_fixture` просит найти пункты о возврате. Ваш код выполняет поиск и добавляет событие. На втором шаге `decide` получает уже непустую историю и возвращает готовый ответ. В настоящем запуске `decide_live` кладёт историю в сообщения для модели, и найденные пункты действительно до неё доходят. Если событие не записать, в следующем запросе этих данных просто не будет.

## Запустим с моделью

Откройте `demo.py` и выберите **Run 'demo'**. Теперь работает весь цикл: модель выбирает действие, программа выполняет его, результат возвращается модели. В Run появятся события и итоговый словарь. Ожидаем ответ по найденным пунктам; точные слова и число шагов могут быть разными. Если запуск закончился статусом `step_limit`, это тоже результат: по событиям видно, что модель делала вместо ответа.

## Проверим функцию отдельно

Откройте `demo_check.py` и выберите **Run 'demo_check'**. Ожидаем статус `completed`, ответ "Найдены три пункта о возврате." и одно событие: команду поиска и её результат. Для готовых проверок запустите `class LessonTests` в `tests/test_lesson.py`.

## Попробуйте сломать

Закомментируйте в своём коде строку с `events.append(...)`, поставив перед ней `#`, и запустите `demo_check.py`. `decide_fixture` будет получать пустую историю, каждый раз заново просить поиск, и цикл закончится статусом `step_limit`. Так выглядит агент, который "не видит" результатов своих действий. Уберите `#`.

## Что мы получили

У помощника появился агентный цикл: модель решает, программа выполняет, результат возвращается модели. Координацию этих шагов называют **оркестрацией**: код решает, когда обратиться к модели, когда выполнить инструмент, что передать дальше и когда остановиться. У нас это обычный цикл Python; в больших системах ту же работу делают библиотеки вроде LangGraph. Подробнее - в [памятке терминов](../terms.md#%D0%BE%D1%80%D0%BA%D0%B5%D1%81%D1%82%D1%80%D0%B0%D1%86%D0%B8%D1%8F).
